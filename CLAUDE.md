# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

This is the **owner's active, in-use blogging platform** at `chat.dailyai.studio` - not a template to experiment with. There are ~180 posts and new posts are added regularly. Treat changes as production-impacting: be conservative with anything that touches the `posts` collection schema or the URL structure (`/posts/[slug]`, `/posts/[slug].md`, `/tags/[tag]`).

Built from the Brook Astro template, now running on **Cloudflare Workers with [EmDash](https://docs.emdashcms.com) as the CMS** (moved from a static Railway build - see [docs/emdash-migration.md](docs/emdash-migration.md) for the cutover runbook and what changed). It used to ship a sitewide chatbot; that was removed entirely - don't reintroduce one without the owner asking.

Node >= 22.12.0 is required (see `engines` in [package.json](package.json)). Astro 7 (EmDash 1.4 requires it).

## Commands

```bash
npm run dev           # Astro dev server on http://localhost:4321 (workerd + local D1 in .wrangler/state)
npm run build         # server build for Cloudflare into dist/
npm run deploy        # astro build && wrangler deploy
npm run seed:build    # regenerate seed/seed.json from src/content/posts
npm run post:publish -- src/content/posts/<slug>.md [--url https://chat.dailyai.studio]
```

First `npm run dev` on a fresh checkout: open `http://localhost:4321/_emdash/api/setup/dev-bypass?content=1` once to import the seed into the local database and sign in as a dev admin. Admin UI: `/_emdash/admin`.

There is no test runner, linter, or formatter configured.

## Architecture

- **Content lives in EmDash, not files.** Posts are the `posts` collection in D1 (binding `DB`); tags are EmDash's `tag` taxonomy; uploaded media goes to R2 (binding `MEDIA`). Fields mirror the old frontmatter: `title`, `date` (datetime), `excerpt`, `image` (cover URL string), `content` (Portable Text), `faq` (repeater of `question`/`answer`), plus `tag_order` (keeps the author's tag order, since EmDash returns terms sorted by label). Schema is defined in `seed/seed.json` (generated by `scripts/build-emdash-seed.mjs`); changing it on a live site is done in the admin or with `emdash schema`, not by editing the seed.
- **`src/content/posts/`** is the archive the seed was built from, and still the place to draft a post as markdown for `npm run post:publish`. Editing a file there does nothing on the live site until it's published.
- **Markdown → Portable Text**: [scripts/lib/post-markdown.mjs](scripts/lib/post-markdown.mjs) (remark + GFM + smartypants, same parsing as the old Astro build). Don't swap in EmDash's `markdownToPortableText` - it drops tables, `*italics*`, `---`, multi-paragraph quotes and bare-URL links.
- **Data access**: everything goes through [src/lib/posts.ts](src/lib/posts.ts) (`getPublishedPosts`, `getPublishedPost`, `neighbours`). It returns the old content-collection shape (`id` = slug, `data` = frontmatter, `body` = markdown) so pages didn't change. EmDash only serves published entries to anonymous requests, so drafts are hidden everywhere.
- **Rendering**: [src/components/PostBody.astro](src/components/PostBody.astro) renders Portable Text with site renderers in `src/components/portable-text/` that reproduce the old markdown HTML (heading `id` slugs via github-slugger, Shiki `github-dark` code with the JS regex engine so it runs on Workers, plain `<img>`, GFM tables, loose lists, `<hr>`). Keep that HTML stable - the theme's prose styles depend on it.
- **Routing**: all pages render on request (`output: 'server'`). `src/pages/posts/[slug].astro`, `posts/[slug].md.ts`, `tags/[tag].astro`, `rss.xml.js`, `llms.txt.ts`, `llms-full.txt.ts`, `journal.md.ts`, `sitemap-index.xml.ts`, `sitemap-0.xml.ts`.
- **Caching**: public routes are cached in the Workers Cache via `routeRules` in [astro.config.mjs](astro.config.mjs), tagged `posts`; EmDash purges that tag on publish. Add a rule for any new public route.
- **Layouts**: [BaseLayout.astro](src/layouts/BaseLayout.astro) owns `<head>` (SEO/OG/JSON-LD, Google Analytics `G-TRGMEDWTJM`, fonts), the site chrome (header/footer, dark-mode toggle, mobile menu), and Astro `<ClientRouter />` view transitions. [PostLayout.astro](src/layouts/PostLayout.astro) wraps it for article pages and computes reading time from the rendered slot HTML.
- **View transitions**: Astro's `<ClientRouter />` is enabled, which means soft-nav between pages. These piggy-back on this and must stay in sync:
  1. Google Analytics fires `gtag('config', ...)` on `astro:page-load` so soft-nav generates pageviews.
  2. Dark-mode reapplies on `astro:after-swap` (theme stored in `localStorage.theme`).
  3. Mobile menu + theme-toggle handlers re-bind on `astro:after-swap`.
  When adding interactive scripts to BaseLayout, follow the same pattern or they will only work on the initial page load.
- **Styling**: Tailwind CSS v4 via `@tailwindcss/vite` (not a `tailwind.config.*` file - config is in CSS via `@theme` in [src/styles/global.css](src/styles/global.css)). The README's mention of `tailwind.config.mjs` is from the upstream template and does not apply here.
- **Images**: files in `public/images/` are served as Workers static assets and referenced as `/images/foo.jpg` (they ship with a deploy). The Cloudflare adapter uses the `passthrough` image service.

## Writing voice for posts

Posts are written in Alfred's first-person practitioner voice — plain-spoken, concrete, no hype. When drafting or editing a post, follow the `alfred-nutile-voice-style` skill. For technical build write-ups and tutorials specifically — anything teaching a developer to build the thing — also follow the `alfred-technical-writing-voice` skill ([.claude/skills/alfred-technical-writing-voice/SKILL.md](.claude/skills/alfred-technical-writing-voice/SKILL.md)): first-person from the trenches, honest about struggle, "let's break it down" pacing over real code, `> NOTE:` asides, real examples (never `foo`/`bar`), and the payoff-first teaching arc. The single most important rule, because it's what most often makes a draft "sound nothing like me":

- **No fake feelings — including the subtle, section-framing kind.** Never invent an emotional reaction Alfred didn't have. Beyond the obvious ("I was blown away," "my jaw dropped," "I'm so proud of this"), this covers the LinkedIn-flavored glue that's harder to spot and just as wrong: "the part I was so worried about," "the scary part of…," "here's the fun part," "that's the part that flips it for me," "the honest mess of running it for real," "it's not always clean," "and then something great happened." Don't editorialize his work as a confession, either — report what happened plainly. A post — especially a technical review — is analysis (tools, trade-offs, build patterns), not a feelings arc. State the point plainly. A real, specific fact ("migration numbering must be contiguous or the deploy is rejected") is fine; a manufactured mood or dramatized struggle is not. Genuine enthusiasm tied to a real event is fine and rare.
- **No condescension or spoon-feeding.** The audience is technical/curious builders who want to know how to build, choose tools, and use AI — not beginners to manage. Don't tell the reader what to notice ("Look down that column," "Notice how…," "See what happened?"), don't re-explain the obvious, don't lecture or throat-clear ("Here's the thing about any real app…"). One-clause jargon glosses are fine; otherwise assume intelligence. Write to a peer.
- **No reader-commanding tics:** "Read that again," "Stay with me," "Think about what that means," "Let that sink in," "Hold that thought."
- **No clichés:** "boil the ocean," "roach motel," "changes the game," "secret sauce."
- **Don't flatten his real conventions.** The `**TLDR:**` callout and genuine enthusiasm tied to a real event are his voice, not AI drift — leave them.

## Post FAQ pattern

Every substantive post gets a `faq:` block in its frontmatter — a short list of `question`/`answer` pairs drawn from what the post actually covers. It renders a visible FAQ section on the page **and** emits `FAQPage` JSON-LD, which AI answer engines pull into "how do I…" results (good for GEO). In markdown it's the `faq:` frontmatter list; in EmDash it's the post's **FAQ** repeater field (`question` / `answer`, plain text).

- Keep questions and answers as **plain prose** — the structured data must match the visible on-page text, so no markdown or links inside answers.
- Pull ~4–6 questions from what the post genuinely supports; don't invent Q&A the post doesn't back up.
- The same voice rules apply, though FAQ answers lean neutral and factual.

Copy the shape from [edge-functions.md](src/content/posts/edge-functions.md) or [evals-stop-guessing-whether-your-ai-works.md](src/content/posts/evals-stop-guessing-whether-your-ai-works.md).

## Deployment

Cloudflare Workers (`wrangler.jsonc`: Worker `dailyai-blog`, D1 `dailyai-blog`, R2 `dailyai-blog-media`, a once-a-minute cron for scheduled publishing). Deploy with `npm run deploy`, or via Workers Builds on push to `main` once that's connected. Publishing a post does not need a deploy; changing code, styles, or files in `public/` does. See [docs/emdash-migration.md](docs/emdash-migration.md).
